القسم الأول: الرؤية العامة للمشروع

1.1 تعريف المشروع

«مورد» منصة إلكترونية متكاملة تتيح للمحلات التجارية طلب البضائع من خلال تطبيق واحد، وتتيح للإدارة التحكم الكامل في المنتجات والأسعار والطلبات والفواتير والحسابات والمدفوعات والتوصيل.

يتكون المشروع من:

1. تطبيق أندرويد أصلي بلغة Java.
2. موقع إلكتروني متكامل يعمل على المتصفحات.
3. تطبيق ويب تقدمي PWA قابل للتثبيت على أجهزة iPhone وAndroid.
4. لوحة إدارة مركزية.
5. نظام حسابات وصلاحيات متعدد المستخدمين.
6. خادم خلفي وقاعدة بيانات مركزية.
7. نظام إشعارات فورية.
8. نظام مالي وفواتير وكشوف حسابات.
9. نظام توصيل وتتبع.
10. نظام تقارير ومراقبة ونسخ احتياطي.

1.2 المبادئ الأساسية

- جميع المنصات تعمل على قاعدة بيانات مركزية واحدة.
- جميع المستخدمين يدخلون من شاشة دخول موحدة.
- النظام يحدد صلاحية المستخدم بعد تسجيل الدخول.
- لا يستطيع أي مستخدم الوصول إلى وظائف أو بيانات خارج صلاحياته.
- الأسعار موحدة لجميع المحلات.
- كل عملية مالية أو تشغيلية يجب أن تكون موثقة.
- كل طلب يجب أن يمتلك رقماً فريداً.
- كل فاتورة يجب أن تحتفظ بنسخة ثابتة من بياناتها المالية.
- لا يتم فقدان الطلبات بسبب ضعف الإنترنت أو إغلاق التطبيق.
- كل تغيير مهم يجب أن يسجل في سجل العمليات.

القسم الثاني: نظام الحسابات الموحد والصلاحيات

هذا القسم من أهم أقسام المشروع، ويجب تنفيذه قبل بقية الوظائف.

2.1 شاشة دخول موحدة

إنشاء شاشة تسجيل دخول واحدة لجميع المستخدمين دون استثناء.

تحتوي على:

- اسم المستخدم أو البريد الإلكتروني أو رقم الهاتف وفق بيانات الحساب.
- كلمة المرور.
- إظهار وإخفاء كلمة المرور.
- تذكر الجلسة بصورة آمنة.
- نسيت كلمة المرور.
- تسجيل الخروج.
- التحقق من حالة الحساب.
- رسائل خطأ واضحة.
- منع محاولات الدخول المتكررة المشبوهة.

لا يتم إنشاء شاشة دخول منفصلة للإدارة أو المحلات أو المندوبين.

2.2 كيف يحدد النظام نوع المستخدم؟

عند تسجيل الدخول بنجاح:

1. يتحقق الخادم من بيانات الحساب.
2. يسترجع هوية المستخدم وحالة حسابه.
3. يسترجع الأدوار والصلاحيات الممنوحة له.
4. يحدد المحل أو المؤسسة المرتبط بها إن وجد.
5. ينشئ جلسة آمنة.
6. يوجه المستخدم تلقائياً إلى الواجهة المناسبة.

أمثلة:

- صاحب محل يدخل ← تظهر لوحة المحل.
- مدير النظام يدخل ← تظهر لوحة الإدارة الرئيسية.
- موظف طلبات يدخل ← تظهر لوحة إدارة الطلبات.
- موظف مالي يدخل ← تظهر لوحة الحسابات والفواتير.
- مندوب توصيل يدخل ← تظهر لوحة التوصيل.
- مدير مخزن يدخل ← تظهر لوحة المنتجات والتجهيز.

مهم: لا تعتمد على إخفاء الأزرار في الواجهة فقط. يجب التحقق من الصلاحيات داخل الخادم عند كل طلب API.

2.3 أنواع الحسابات والأدوار

أ. مالك النظام Super Admin

أعلى صلاحية في المنصة.

الصلاحيات:

- الوصول إلى جميع أقسام النظام.
- إنشاء حسابات الإدارة.
- تعيين مديري النظام.
- إنشاء الأدوار والصلاحيات.
- إنشاء المحلات وإدارتها.
- إدارة جميع المنتجات والأسعار.
- إدارة جميع الطلبات.
- إدارة الفواتير والمدفوعات والديون.
- إدارة التوصيل والمندوبين.
- الاطلاع على جميع التقارير.
- ضبط ساعات العمل ومهلة التوصيل.
- إعدادات الإشعارات.
- الاطلاع على سجل النشاطات.
- إدارة النسخ الاحتياطية.
- إيقاف الحسابات.
- التحكم في إعدادات النظام.

لا يجوز إنشاء حساب آخر بهذه الصلاحية إلا بموافقة مالك النظام أو إجراء إداري محمي.

ب. مدير الإدارة Admin Manager

- إدارة موظفي الإدارة ضمن الصلاحيات الممنوحة.
- مراجعة الطلبات واعتمادها.
- متابعة عمليات التجهيز.
- إدارة المحلات.
- إدارة التوصيل.
- الاطلاع على التقارير.
- لا يستطيع تغيير إعدادات المالك الحساسة إلا إذا مُنح صلاحية صريحة.

ج. موظف الطلبات Orders Employee

- مشاهدة الطلبات المسموح بها.
- مراجعة الأصناف والكميات.
- قبول الطلب أو رفضه وفق السياسة.
- إرسال الطلب إلى التجهيز.
- إضافة ملاحظات داخلية.
- تحديث حالة الطلب.
- مشاهدة بيانات المحل اللازمة للعمل.
- لا يستطيع تعديل الحسابات المالية أو إنشاء دفعات إلا بتفويض.

د. موظف المنتجات والمخزون

- إضافة المنتجات.
- تعديل أسماء المنتجات وصورها.
- إدارة التصنيفات.
- إدارة وحدات البيع والتحويل.
- تغيير حالة التوفر.
- إدارة العروض وفق الصلاحيات.
- لا يستطيع الاطلاع على المعلومات المالية الحساسة إلا إذا مُنح ذلك.

هـ. الموظف المالي Accountant

- عرض الفواتير.
- تسجيل الدفعات.
- تسجيل التحصيلات.
- عرض أرصدة المحلات.
- إعداد كشوف الحسابات.
- تسجيل التسويات المالية وفق الصلاحية.
- إصدار تقارير مالية.
- لا يستطيع تعديل الطلبات بعد إصدار الفواتير.

و. مسؤول التوصيل Delivery Manager

- عرض الطلبات الجاهزة للتوصيل.
- توزيع الطلبات على المندوبين.
- تعيين مواعيد التوصيل.
- متابعة المندوبين.
- مشاهدة مواقع التوصيل.
- متابعة الطلبات المتأخرة.
- إدارة حالات التوصيل.

ز. مندوب التوصيل Delivery Agent

- مشاهدة الطلبات المسندة إليه فقط.
- مشاهدة اسم المحل وعنوانه ورقم التواصل.
- مشاهدة تفاصيل الطلب الضرورية.
- فتح الملاحة.
- تحديث حالة التوصيل.
- مشاركة موقعه خلال المهمة عند الموافقة وتفعيل الخاصية.
- تأكيد التسليم.
- تسجيل المبالغ المحصلة نقداً إذا كان مخولاً بذلك.
- رفع إثبات التسليم عند الحاجة.

لا يستطيع المندوب مشاهدة الحسابات المالية الكاملة للمحلات أو تعديل الأسعار أو المنتجات.

ح. صاحب المحل Shop Owner

- مشاهدة المنتجات والأسعار الموحدة.
- البحث والتصفح.
- إضافة المنتجات إلى السلة.
- إرسال طلبات الشراء.
- متابعة حالة الطلب.
- مشاهدة العروض.
- مشاهدة الفواتير.
- الاطلاع على كشف حساب محله.
- مشاهدة الديون والمدفوعات.
- إدارة موظفي محله إذا سمحت الإدارة بذلك.
- تعديل بيانات المحل المسموح بتعديلها.
- استقبال الإشعارات.

ط. موظف المحل Shop Employee

- تصفح المنتجات.
- إنشاء مسودة طلب.
- إعداد السلة.
- إرسال الطلب إذا مُنح صلاحية الإرسال.
- متابعة الطلبات المسموح له بها.
- مشاهدة الفواتير إذا مُنح الصلاحية.
- لا يستطيع تعديل بيانات الحساب الرئيسية أو إدارة الديون إلا بتفويض.

2.4 إدارة المستخدمين والصلاحيات

إنشاء وحدة مركزية باسم «المستخدمون والصلاحيات».

يجب أن تدعم:

- إضافة مستخدم.
- تعديل بيانات المستخدم.
- تفعيل وإيقاف المستخدم.
- ربط المستخدم بمحل أو أكثر حسب طبيعة عمله.
- تعيين دور واحد أو أكثر.
- تخصيص صلاحيات مستقلة.
- تحديد الأقسام التي يمكنه مشاهدتها.
- تحديد العمليات التي يمكنه تنفيذها.
- تحديد العمليات التي تحتاج موافقة مدير.
- تحديد تاريخ انتهاء الحساب عند الحاجة.
- إعادة تعيين كلمة المرور.
- إلغاء جميع جلسات المستخدم عند الضرورة.

نظام الصلاحيات الدقيقة RBAC

لا تعتمد على أسماء الأدوار وحدها.

يجب وجود صلاحيات مستقلة مثل:

- products.view
- products.create
- products.update
- products.delete
- products.availability.update
- orders.view
- orders.create
- orders.confirm
- orders.reject
- orders.cancel
- orders.prepare
- orders.dispatch
- invoices.view
- invoices.create
- payments.create
- payments.reverse
- accounts.view
- accounts.adjust
- users.manage
- roles.manage
- reports.view
- settings.manage
- audit.view

يمكن إضافة صلاحيات جديدة دون إعادة بناء التطبيق.

2.5 الحسابات متعددة الأدوار

قد يكون الشخص موظفاً في الإدارة ومسؤولاً عن قسم آخر، لذلك يجب دعم تعدد الأدوار.

إذا كان المستخدم يمتلك أكثر من دور:

- يتم دمج الصلاحيات المسموح بها وفق سياسة واضحة.
- تظهر له الأقسام المصرح بها فقط.
- يمكن عرض اختيار سياق العمل عند الحاجة.
- يجب تسجيل الدور والسياق الذي نفذ المستخدم العملية من خلاله.

لا تمنح أي حساب صلاحيات أعلى لمجرد تغيير قيمة مخفية في التطبيق.

2.6 إنشاء حساب المحل

عند تسجيل محل جديد، يقوم مالك النظام أو الموظف المخول بإدخال:

- اسم المحل التجاري.
- اسم صاحب المحل.
- رقم الهاتف الأساسي.
- رقم بديل اختياري.
- المنطقة والمدينة.
- العنوان التفصيلي.
- الموقع الجغرافي.
- اسم المستخدم.
- كلمة المرور المؤقتة أو رابط إنشاء كلمة المرور.
- حالة الحساب.
- شروط الدفع المسموح بها.
- حد الائتمان إن تم تفعيل نظامه.
- ملاحظات إدارية.
- تاريخ التسجيل.

يتم ربط الحساب بالمحل بصورة واضحة.

2.7 إدارة موظفي المحلات

يستطيع صاحب المحل إنشاء حسابات لموظفيه إذا سمحت الإدارة.

مثال:

- حساب صاحب المحل.
- حساب موظف صباحي.
- حساب موظف مسائي.

مع إمكانية تحديد:

- من يستطيع إنشاء الطلبات.
- من يستطيع إرسال الطلب.
- من يستطيع مشاهدة الفواتير.
- من يستطيع مشاهدة كشف الحساب.
- من يستطيع إدارة موظفي المحل.

القسم الثالث: إدارة المنتجات والتصنيفات

3.1 التصنيفات الأساسية

يبدأ النظام بتصنيفات قابلة للتعديل والإضافة:

1. المجمدات.
2. المواد التموينية والأساسية.
3. الألبان والأجبان.
4. المكسرات والمسليات والحلويات.
5. المشروبات والعصائر.
6. المنظفات ومواد التنظيف.
7. مستلزمات الأطفال.
8. العناية الشخصية.
9. الخضروات والفواكه والبيض.
10. الأدوات المنزلية والاستهلاكية.
11. المعلبات.
12. البهارات والمواد الإضافية.

يمكن للإدارة:

- إضافة تصنيف.
- تعديل التصنيف.
- حذف التصنيف إذا لم يرتبط بمنتجات أو بعد نقله بصورة آمنة.
- ترتيب التصنيفات.
- إضافة صورة أو أيقونة.
- إخفاء تصنيف مؤقتاً.
- إنشاء تصنيفات فرعية.

3.2 بيانات المنتج

كل منتج يجب أن يحتوي على:

- معرف فريد Product ID.
- اسم المنتج.
- اسم بديل للبحث إن وجد.
- وصف المنتج.
- صورة رئيسية.
- صور إضافية اختيارية.
- التصنيف.
- العلامة التجارية عند وجودها.
- رمز المنتج SKU.
- باركود اختياري.
- سعر البيع.
- وحدة البيع.
- الوحدات الإضافية.
- معامل التحويل.
- الحد الأدنى للطلب.
- حالة التوفر.
- حالة الظهور.
- ترتيب العرض.
- تاريخ الإنشاء والتعديل.

3.3 الصور

- دعم رفع الصور من الجهاز.
- ضغط الصور وتحسينها تلقائياً.
- إنشاء صور مصغرة.
- منع الملفات غير الآمنة.
- التحقق من نوع وحجم الصورة.
- تخزين الصور في خدمة ملفات مستقلة.
- الاحتفاظ بالصورة الأصلية والنسخة المحسنة عند الحاجة.
- عدم تخزين الصور الكبيرة داخل قاعدة البيانات.
- توفير صورة بديلة عند عدم وجود صورة.
- دعم استيراد مجموعة صور للمنتجات.

لا يسمح بإضافة منتج بصور وهمية أو صور لا تخص المنتج في النسخة التجارية النهائية.

3.4 نظام وحدات البيع

يجب إنشاء نظام مرن للوحدات، وليس حقلاً ثابتاً باسم الوحدة.

أنواع الوحدات:

- حبة.
- كيلوغرام.
- غرام.
- نصف كيلو.
- لتر.
- ملليلتر.
- عبوة.
- علبة.
- كيس.
- شوال.
- كرتونة.
- دستة.
- جالون.

مثال:
منتج جبنة فيتا:

- الوحدة الأساسية: علبة.
- وحدة إضافية: كرتونة.
- الكرتونة = 12 علبة.
- سعر العلبة مستقل.
- سعر الكرتونة مستقل.

مثال:
مكسرات:

- كيلو.
- نصف كيلو.
- ربع كيلو.

مثال:
عصا مكنسة:

- حبة.
- دستة = 12 حبة.

يجب أن يحدد مسؤول المنتجات الوحدات المسموح بها لكل صنف، ولا تظهر للمستخدم وحدات غير مرتبطة بذلك الصنف.

قواعد حسابية

- لا يجوز قبول كمية صفر أو كمية سالبة.
- دعم الكسور للوزن والسوائل عند الحاجة.
- منع الكسور للأصناف التي تباع حصراً بالعدد الصحيح.
- حفظ الوحدة التي اختارها العميل داخل الطلب.
- حفظ معامل التحويل وقت الطلب.
- عرض الكمية بصورة مفهومة في السلة والفاتورة.
- عدم افتراض أن جميع الكراتين تحتوي العدد نفسه.

3.5 التسعير

النظام يعتمد سعراً موحداً لجميع المحلات.

- لكل منتج سعر عام.
- لكل وحدة بيع سعر محدد.
- تعديل السعر من الإدارة فقط.
- لا يوجد تسعير سري مختلف لكل محل.
- يمكن تقديم خصم من خلال العروض المعتمدة.
- يجب عرض السعر والوحدة بوضوح.
- يتم حفظ السعر وبيانات الخصم وقت اعتماد الطلب.
- لا يؤثر تغيير السعر على الفواتير السابقة.

القسم الرابع: واجهة صاحب المحل

4.1 الصفحة الرئيسية

تحتوي على:

- شعار مورد.
- اسم المحل.
- إشعارات الطلبات.
- مربع بحث بارز.
- تصنيفات المنتجات في الجزء العلوي.
- عروض وخصومات.
- المنتجات المميزة.
- المنتجات المتاحة.
- المنتجات الأكثر طلباً.
- زر السلة مع عدد الأصناف.
- شريط تنقل سفلي.

4.2 تجربة البحث

يجب أن يدعم البحث:

- اسم المنتج.
- جزء من الاسم.
- الاسم البديل.
- العلامة التجارية.
- رمز المنتج.
- البحث باللغة العربية والإنجليزية.
- معالجة اختلافات الهمزات والتشكيل قدر الإمكان.
- تصفية النتائج حسب التصنيف والتوفر.

4.3 بطاقة المنتج

تحتوي على:

- صورة المنتج.
- الاسم.
- السعر.
- الوحدة.
- حالة التوفر.
- اختيار الوحدة عند تعدد الوحدات.
- إدخال الكمية.
- زر الإضافة إلى السلة.

إذا كان الصنف غير متوفر:

- يظهر بوضوح أنه غير متوفر.
- يتعطل زر الإضافة.
- لا يسمح بإرساله ضمن الطلب.

4.4 سلة المشتريات

تحتوي على:

- قائمة الأصناف.
- صورة واسم كل صنف.
- الوحدة المختارة.
- الكمية.
- سعر الوحدة.
- إجمالي الصنف.
- تعديل الكمية.
- حذف الصنف.
- الملاحظات.
- الخصومات.
- الإجمالي النهائي.

يجب تحديث الإجمالي تلقائياً بعد كل تغيير.

إذا تغير سعر المنتج قبل تأكيد الطلب، يجب تنبيه صاحب المحل وعرض السعر الجديد وطلب موافقته.

4.5 إرسال الطلب

صفحة تأكيد الطلب تتضمن:

- بيانات المحل.
- عنوان التوصيل.
- تفاصيل الأصناف.
- إجمالي المبلغ.
- العروض والخصومات.
- طريقة الدفع.
- الملاحظات العامة.
- موعد التوصيل المتوقع وفق ساعات العمل.
- زر تأكيد وإرسال الطلب.

يجب منع الضغط المتكرر من إنشاء أكثر من طلب.

بعد الإرسال:

- يعرض رقم الطلب.
- يظهر إشعار نجاح واضح.
- ينتقل المستخدم إلى تفاصيل الطلب.
- يرسل النظام إشعاراً للإدارة.

القسم الخامس: إدارة الطلبات

5.1 دورة حياة الطلب

الحالات الرسمية:

1. جديد.
2. قيد المراجعة.
3. بانتظار موافقة المحل عند تغيير الكميات أو الأسعار أو البدائل.
4. تم التأكيد.
5. قيد التجهيز.
6. جاهز للتسليم للمندوب.
7. خرج للتوصيل.
8. في الطريق.
9. تم التسليم.
10. مكتمل مالياً عند استيفاء المبلغ المستحق.
11. ملغي.
12. مرفوض.
13. متعذر التسليم.
14. مرتجع جزئياً أو كلياً عند الحاجة.

يجب ألا يتم الانتقال بين الحالات بصورة عشوائية. يجب تحديد الحالات المسموح الانتقال إليها ومن يملك صلاحية ذلك.

5.2 لوحة الطلبات للإدارة

تعرض:

- رقم الطلب.
- اسم المحل.
- وقت الإرسال.
- عدد الأصناف.
- إجمالي المبلغ.
- طريقة الدفع.
- حالة الطلب.
- الوقت المتبقي المتوقع.
- الموظف المسؤول.
- المندوب إن تم تعيينه.

مع فلاتر:

- الطلبات الجديدة.
- قيد المراجعة.
- قيد التجهيز.
- جاهزة للتوصيل.
- قيد التوصيل.
- المكتملة.
- الملغاة.
- المتأخرة.

5.3 تفاصيل الطلب

تتضمن:

- بيانات المحل.
- بيانات التواصل.
- الأصناف.
- الوحدات.
- الكميات.
- الأسعار.
- الخصومات.
- الملاحظات.
- سجل حالات الطلب.
- سجل الموظفين الذين تعاملوا معه.
- بيانات التوصيل.
- الفاتورة المرتبطة.
- المدفوعات المرتبطة.

5.4 تعديل الطلب

إذا اكتشفت الإدارة عدم توفر صنف أو خطأ في الكمية:

- لا يتم حذف الصنف أو استبداله بصمت.
- يتم تسجيل التعديل.
- يتم توضيح سبب التعديل.
- يتم إشعار صاحب المحل.
- إذا تغير السعر أو الإجمالي أو البديل، يجب الحصول على موافقة المحل قبل الاعتماد.
- يحفظ النظام النسخة السابقة والتعديل الجديد.

5.5 الإلغاء

- يستطيع المحل طلب الإلغاء وفق سياسة الطلب.
- يمكن للإدارة إلغاء الطلب مع تسجيل السبب.
- لا يجوز إلغاء طلب تم تسليمه دون إنشاء إجراء مرتجع أو تسوية.
- إذا صدرت فاتورة أو سجلت دفعة، يجب معالجة الأثر المالي بشكل صحيح.

القسم السابع: ساعات العمل والمهلة الزمنية

7.1 ساعات العمل

تحدد الإدارة:

- أيام العمل.
- وقت بدء استقبال الطلبات.
- وقت إيقاف استقبال الطلبات.
- العطلات.
- الإغلاق الاستثنائي.
- ساعات التوصيل.
- مدة التجهيز الافتراضية.

الإعداد الأولي المقترح:

- بداية العمل: 06:00 صباحاً.
- نهاية العمل: 11:00 مساءً.
- مهلة التوصيل المستهدفة: 6 ساعات عمل.

هذه القيم قابلة للتعديل من لوحة الإدارة.

7.2 حساب المهلة

لا يبدأ احتساب الست ساعات من وقت الطلب إذا تم إرساله خارج ساعات العمل.

مثال:

- إرسال الطلب الساعة 12:00 ليلاً.
- بداية العمل الساعة 06:00 صباحاً.
- يبدأ احتساب المهلة من السادسة صباحاً.

يجب أن يأخذ النظام في الحسبان:

- أيام العطلات.
- الإغلاق.
- ساعات استقبال الطلبات.
- التوقفات الاستثنائية.
- تغيير موعد التوصيل يدوياً.
- اختلاف توقيت المناطق مستقبلاً.

7.3 التايمر

يعرض لصاحب المحل:

- وقت إرسال الطلب.
- وقت بدء احتساب المهلة.
- موعد الوصول المتوقع.
- الوقت المتبقي.
- الوقت المنقضي.
- حالة الطلب.

لا يعرض موعداً وهمياً. إذا لم يتم تحديد موعد مؤكد، يجب توضيح أنه موعد تقديري.

عند تجاوز المهلة:

- يظهر الطلب كمتأخر.
- يصل تنبيه لمسؤول الطلبات.
- يتم توضيح سبب التأخير.
- يتم تحديث الموعد المتوقع.
- يتم إشعار المحل.

القسم التاسع: النظام المالي والفواتير

9.1 الفاتورة

تحتوي على:

- رقم فاتورة فريد.
- رقم الطلب المرتبط.
- بيانات المورد.

- حالة الفاتورة.

تحتفظ الفاتورة بنسخة ثابتة من تفاصيل الأسعار والمنتجات وقت إصدارها.

9.2 الدفع النقدي والآجل

يتم تحديد طريقة الدفع لكل طلب:

نقدي:

- المبلغ مستحق عند التسليم أو حسب سياسة التحصيل.
- يسجل المبلغ المحصل.
- يظهر المتبقي إن لم يتم التحصيل كاملاً.

آجل:

- يتم تسجيل المبلغ المستحق على حساب المحل.
- يظهر في كشف الحساب.
- يمكن تسجيل دفعات لاحقة.
- يمكن تحديد تاريخ استحقاق.

لا يجوز اعتبار الطلب الآجل مدفوعاً لمجرد تأكيده.

9.3 الدفعات والتحصيلات

كل حركة مالية يجب أن تتضمن:

- رقم الحركة.
- المحل.
- القيمة.
- نوع الحركة.
- طريقة الدفع.
- التاريخ والوقت.
- الموظف الذي سجلها.
- رقم الفاتورة أو المرجع.
- ملاحظات.
- إثبات اختياري.

طرق الدفع الأولية:

- نقداً.
- تحويل بنكي عند تفعيل هذه الطريقة.
- وسيلة أخرى تضيفها الإدارة.

9.4 كشف الحساب

لكل محل كشف حساب مستقل يحتوي على:

- الرصيد الافتتاحي.
- الفواتير.
- المشتريات.
- الدفعات.
- التسويات.
- المرتجعات.
- الرصيد الحالي.
- الرصيد المستحق.

مع إمكانية:

- تحديد الفترة.
- البحث.
- تصفية الحركات.
- تصدير PDF.
- الطباعة.
- مشاركة الكشف.

القاعدة الحسابية

الرصيد المستحق = إجمالي الفواتير والرسوم المعتمدة - الدفعات والتسويات الدائنة المعتمدة.

إذا دفع المحل مبلغاً أكبر من المستحق:

- لا يضيع الفرق.
- يسجل كرصيد دائن للمحل.
- يستخدم في الفواتير القادمة.
- يظهر بوضوح في كشف الحساب.

9.5 حد الائتمان

إضافة إعداد اختياري لكل محل:

- حد ائتماني.
- الرصيد الحالي.
- المبلغ المتاح.
- تنبيه عند الاقتراب من الحد.
- منع الطلب الآجل عند تجاوز الحد وفق إعدادات الإدارة.

لا يتم رفض الطلب النقدي بسبب تجاوز الحد الائتماني.

9.6 تصحيح الأخطاء المالية

لا يتم حذف دفعة مالية معتمدة أو تعديلها بصمت.

عند الخطأ:

- إنشاء حركة عكسية أو تسوية.
- ذكر سبب التصحيح.
- تسجيل الموظف.
- حفظ الحركة الأصلية.
- حفظ الحركة التصحيحية.
- إظهار الأثر النهائي في كشف الحساب.

الخاتمة والتوجيه التنفيذي

مشروع مورد ليس مجرد متجر إلكتروني، بل نظام تجاري متكامل يجمع بين البيع بالجملة وإدارة العملاء التجاريين والطلبات والتوزيع والمحاسبة.

الأولوية هي بناء نظام موثوق تكون فيه قاعدة البيانات والخادم المركزي هما مصدر الحقيقة لجميع الأجهزة.

ترتيب التنفيذ الإلزامي:

1. تحليل المتطلبات وإعداد مخطط قاعدة البيانات.
2. إنشاء نظام الدخول الموحد والأدوار والصلاحيات.
3. بناء Backend وواجهات API.
4. إنشاء إدارة المحلات والمنتجات والتصنيفات.
5. بناء تطبيق صاحب المحل.
6. بناء إدارة الطلبات والإشعارات.
7. بناء التوصيل والخرائط والمهلة الزمنية.
8. بناء الفواتير والدفعات وكشوف الحسابات.
9. بناء لوحة الإدارة والتقارير.
10. إنشاء الويب وPWA وربطهما بالخادم.
11. اختبارات الجودة والأمان والأداء.
12. نشر النظام وإصدار APK Release النهائي.

شرط الإنجاز: لا يتم إعلان اكتمال المشروع إلا بعد اختبار دورة العمل الكاملة من إنشاء حساب محل وحتى تسليم الطلب وإصدار الفاتورة وتسجيل الدفع وظهور الحركة في كشف الحساب.
