# معمارية مورد — Firebase + Cloudflare Workers

## الصورة العامة
```
Android (Kotlin + Compose)   Web/PWA (React + TS)
        │  قراءة حيّة مقيّدة بالقواعد        │
        ├──────────► Firestore ◄────────────┤
        │                ▲ كتابة فقط عبر service account
        │  كل كتابة/عملية │
        └──────► Cloudflare Worker «mawred-api» (HTTPS) ◄──┘
                   │ تحقق ID token ← حالة الحساب ← RBAC ← منطق الأعمال ← معاملة Firestore ← سجل تدقيق
                   ├── Firebase Auth (Identity Toolkit REST)
                   ├── FCM HTTP v1 (إشعارات)
                   ├── R2 (صور المنتجات، إثباتات التسليم، النسخ الاحتياطية المشفرة)
                   ├── KV (حدود المعدل، مفاتيح idempotency القصيرة)
                   └── Cron Triggers (التأخير، إعادة محاولة الإشعارات، النسخ اليومي)
```

## مبادئ التنفيذ (تطبيق SRS 1.2 و22)
1. **الخادم مصدر الحقيقة.** Firestore Rules تمنع أي كتابة من العميل (`allow write: if false`) على كل المجموعات. كل تعديل يمر عبر Worker الذي يكتب بحساب خدمة.
2. **القراءة المباشرة مقيّدة.** العميل يقرأ فقط ما تسمح به القواعد (محل يرى محله، مندوب يرى مهامه، موظف حسب custom claims). هذا يمنح تحديثاً حياً وتخزيناً بلا نت دون منح صلاحية كتابة.
3. **RBAC على الخادم في كل طلب.** Worker يقرأ وثيقة المستخدم (الحالة، الأدوار، الاستثناءات، المحلات) في كل طلب ولا يثق بأي قيمة من العميل؛ custom claims نسخة مختصرة للقواعد فقط وتُجدَّد عند أي تغيير.
4. **المال بأعداد صحيحة.** الأسعار بالأغورة (int)، الكميات بالألف (`qtyMilli`) لدعم الكسور. سطر = `round_half_up(qtyMilli × unitPrice / 1000)`. لا float في أي مسار مالي.
5. **دفتر حسابات append-only.** `ledger` لا يُعدَّل ولا يُحذف؛ التصحيح بحركة عكسية تشير للأصل. الرصيد المخزَّن في `shops/{id}.balance` يُحدَّث في نفس المعاملة ويُتحقق منه دورياً بإعادة الجمع.
6. **لقطات ثابتة.** الطلب عند التأكيد والفاتورة عند الإصدار يحفظان الاسم والوحدة والمعامل والسعر والخصم كما هي؛ تغيير السعر لاحقاً لا يمسّها.
7. **عدم التكرار.** كل عملية حساسة تحمل `Idempotency-Key` (UUID من العميل)؛ الخادم يخزن النتيجة في `idempotency/{key}` داخل نفس المعاملة ويعيدها عند التكرار (سيناريو 19.3-4).
8. **إعادة الحساب.** الخادم يتجاهل أي إجمالي يرسله العميل ويعيد حسابه من الأسعار والعروض الحالية؛ إذا اختلف عمّا رآه المستخدم يُرجع `409 PRICE_CHANGED` مع الأسعار الجديدة لطلب موافقته (SRS 4.4).
9. **سجل تدقيق** لكل كتابة: الفاعل، الدور والسياق، العملية، الكيان، قبل/بعد، IP، الجهاز، النتيجة. لا يقرأه إلا `audit.view` ولا يكتبه إلا Worker.
10. **offline:** السلة والمسودات في Room على أندرويد وIndexedDB على الويب بحالة «غير مرسلة» حتى يرد الخادم بنجاح؛ لا دين ولا طلب معتمد محلياً.

## الدخول الموحد
- `POST /auth/login {identifier, password}`: الـWorker يحوّل اسم المستخدم/الهاتف/البريد إلى البريد الداخلي (`u<uid>@login.mawred` إن لم يكن للحساب بريد)، يفحص حد المحاولات في KV (5 فشل/15 دقيقة لكل معرّف + لكل IP)، يتحقق بكلمة المرور عبر Identity Toolkit، يفحص الحالة وتاريخ الانتهاء، ثم يعيد **custom token** + ملخص الصلاحيات و`home`.
- العميل يدخل بـ`signInWithCustomToken`؛ تذكّر الجلسة = refresh token تديره مكتبة Firebase (مخزن مشفّر على أندرويد).
- الإيقاف/تغيير كلمة المرور/«إلغاء كل الجلسات»: Worker يعطّل أو يلغي refresh tokens ويسجّل `sessionsRevokedAt`؛ أي ID token صادر قبله يُرفض.
- نسيت كلمة المرور: حساب ببريد ← رابط إعادة تعيين Firebase. حساب بلا بريد ← تذكرة لمسؤول المستخدمين يصدر كلمة مؤقتة تُجبر على التغيير عند أول دخول.
- MFA للحسابات الإدارية: TOTP عبر Identity Platform (مرحلة لاحقة، انظر الانحرافات).

## التوجيه بعد الدخول
`home` من الدور ذي الأولوية الأعلى؛ متعدد الأدوار يرى اتحاد الصلاحيات (grant ∪ roles) − deny، ويختار سياق العمل إن تعارضت الواجهات. السياق يُرسَل في ترويسة `X-Work-Context` ويُسجَّل في التدقيق ولا يمنح أي صلاحية.

## الصور والملفات
**صور المنتجات مفرّغة دائماً (قرار ساجد 2026-11-20):** كل صورة منتج تُحفظ بخلفية شفافة وتظهر على خلفية البطاقة الموحدة في كل الواجهات.
- Android (لوحة الإدارة): التفريغ على الجهاز بـML Kit Subject Segmentation (مجاني، يعمل بلا نت بعد تنزيل النموذج) ← معاينة على خلفية البطاقة ← تعديل يدوي بالفرشاة عند الحاجة ← حفظ.
- الويب (لوحة الإدارة): تفريغ بالمتصفح للصور ذات الخلفية المتجانسة (ملء من الحواف بتسامح لوني + تنعيم الحواف) مع فرشاة تصحيح، أو رفع PNG/WebP شفاف جاهز. لا مكتبات AGPL لأن المنتج يُباع white-label.
- استيراد دفعة: مجلد صور ← تفريغ آلي متتابع على أندرويد ← مراجعة سريعة ← ربط كل صورة بمنتجها بالـSKU أو الاسم.
- الخادم يرفض صورة منتج بلا قناة شفافية (فحص ترويسة WebP/PNG) ويحفظ `cutout: true`؛ بمجرد الحفظ تظهر للجميع لأن العملاء يقرؤون المنتج حيّاً من Firestore.
- لا صور وهمية أو مأخوذة من منتجات أخرى (SRS 3.3)؛ الكتالوج يبدأ فارغاً وتُضاف الصور الحقيقية مع المنتجات.

ضغط وتصغير على الجهاز (WebP ≤ 1600px + مصغّرة 320px) ← رفع إلى Worker ← فحص النوع بالبايتات السحرية والحجم (≤ 5MB) ← R2 بمفتاح غير قابل للتخمين. صور المنتجات عامة عبر CDN؛ إثباتات التسليم والفواتير خاصة بروابط موقّعة قصيرة العمر.

## الإشعارات
`notifications` (صندوق داخل التطبيق لكل مستخدم) + `notificationJobs` (حالة الإرسال، المحاولات، مفتاح dedupe). FCM HTTP v1؛ الرموز غير الصالحة تُحذف؛ Cron يعيد المحاولة بتراجع أسّي. الإرسال لا يُعدّ دليل استلام. الويب: Web Push عبر FCM حيث يدعمه المتصفح.

## المهلة الزمنية
دالة نقية `computeDueAt(submittedAt, settings)` تبدأ العد من أول دقيقة عمل بعد الإرسال وتتخطى خارج الساعات والعطلات والإغلاق الاستثنائي، وتعيد `estimated: true` ما لم يحدد موظف موعداً مؤكداً. Cron كل 5 دقائق يعلّم المتأخر ويرسل التنبيهات.

## التوصيل والتتبع
التتبع يبدأ فقط عند `on_the_way` وبموافقة المندوب، ويُكتب كل 30–60 ثانية في `deliveryTracks/{orderId}` ويتوقف تلقائياً عند التسليم/التعذر. الخريطة ليست شرطاً لإتمام أي طلب.

## النسخ الاحتياطي
Cron يومي: تصدير كل المجموعات إلى JSON، ضغط، تشفير AES-256-GCM بمفتاح سري في Worker، رفع إلى R2 (حساب/دلو منفصل)، تسجيل في `backupLogs`، تنبيه عند الفشل. احتفاظ 30 يوماً قابل للضبط. سكربت استعادة موثق ومختبر في بيئة staging (RPO ≤ 24 ساعة، RTO ≤ 4 ساعات).

## البيئات
مشروعان منفصلان: `mawred-staging` و`mawred-prod` (Firebase + Worker + R2 لكل منهما). لا أسرار في المستودع؛ أسرار Worker عبر `wrangler secret`، وأسرار CI في GitHub Secrets.

## هيكل المستودع (monorepo)
| المجلد | المحتوى |
|---|---|
| `spec/` | الصلاحيات، الأدوار، آلة حالات الطلب، البيانات الأولية — مصدر واحد يقرأه الخادم والتطبيقات |

| `web/` | React + TS + Vite، PWA |
| `docs/` | المواصفات والمعمارية والأدلة |
